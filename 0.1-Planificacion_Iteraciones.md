## Sobre este Documento

El desarrollo de sistemas intensivos en software se basa en un **proceso iterativo e incremental**, que consiste en la ejecución sucesiva de las tareas de Análisis, Diseño, Construcción y Pruebas a lo largo de múltiples iteraciones. Este enfoque, propio de la metodología **Proceso Unificado (PU)** adoptada por la cátedra, permite validar tempranamente las decisiones arquitectónicas, ajustar el alcance según lo que revele el relevamiento y entregar funcionalidad incremental al cliente.

El presente documento describe el **Plan de Iteración** previsto para el proyecto SPLG (Sistema de Pedidos y Logística de Garrafas de Gas). Recoge:

1. **Estado actual del proyecto** — porcentaje de evaluación de los artefactos, problemas no resueltos y fallas detectadas en iteraciones previas.
2. **Artefactos a producir o refinar** en cada iteración, indicando los porcentajes de evaluación que se han de alcanzar al cierre.
3. **Requisitos suplementarios** — criterios de calidad, restricciones técnicas y consideraciones que aplican a la iteración.
4. **Pautas de evaluación** sobre las que se determinan los puntajes de cada artefacto.

Al término de cada iteración se realizan las evaluaciones pertinentes, cuyos resultados se reseñan en el documento "Cierre de Iteración" con igual código de iteración.

### Configuración de la Iteración

Se entiende por *Configuración de la Iteración* la información que define y da forma a las actividades, metas y características de la misma. Los parámetros que dan forma a cada iteración son:

- **Identificación**: código, fase a la que pertenece, fecha de inicio y cierre.
- **Metas**: objetivos específicos que persigue la iteración.
- **Artefactos nuevos**: documentos o modelos que se inician en la iteración.
- **Artefactos actualizados**: artefactos pre-existentes que se refinan o completan.
- **Problemas a resolver**: errores o pendientes heredados de iteraciones anteriores.

### Pautas de Evaluación

El puntaje de un artefacto es el porcentaje de sus elementos que cumplen los criterios de la tabla siguiente, y se determina al cierre de cada iteración. Los puntajes «Actual» y «Meta» de las tablas de artefactos de este documento se expresan con esta escala.

| Puntaje | Criterio |
|:-------:|----------|
| 0 % | El artefacto no se inició. |
| 25 % | Existe un borrador con la estructura de la plantilla de la cátedra, sin contenido completo. |
| 50 % | Contenido completo, sin comprobar contra el sistema ni contra los demás artefactos. |
| 75 % | Contenido comprobado contra el sistema en funcionamiento (la API levantada) y coherente con los demás artefactos: mismos nombres, códigos y cifras. |
| 90 % | Revisado por una persona distinta de quien lo escribió, con los hallazgos resueltos. |
| 100 % | Aprobado por el docente y sin observaciones pendientes. |

Criterios propios de cada tipo de artefacto:

- **Documentos (Documentos 0 a 3):** cumplen la plantilla de la cátedra, se verifican con el verificador de conformidad del repositorio (todos los chequeos en verde), sus figuras están numeradas y todo caso de uso del catálogo tiene sus cuatro artefactos: caso de uso de alto nivel, caso de uso expandido, diagrama de secuencia del sistema y diagrama de interacción de diseño.
- **Código del sistema (backend, panel y aplicaciones):** pasa las pruebas automáticas y el análisis estático, se prueba contra la aplicación corriendo recorriendo el circuito completo (alta, uso, baja y reintentos) y se revisa antes de integrarse.
- **Modelos (conceptual, de datos y de clases de diseño):** coinciden con el sistema construido; lo no construido se distingue como planificado.
- **Hitos de fase:** se cumplen cuando se cumplen todos los criterios de aceptación listados en la iteración que los cierra.

### Requisitos Suplementarios

- El sistema debe soportar al menos 3 tipos de usuario con roles diferenciados (Cliente, Chofer, Administrador) y un actor automático.
- La asignación de choferes debe ser automática, basada en geolocalización en tiempo real sin intervención del operador.
- El sistema debe funcionar con conexión a internet (4G mínimo para apps móviles).
- El backend debe ser desplegable con Docker Compose en un servidor virtual (VPS).
- La arquitectura debe soportar WebSockets para comunicación bidireccional en tiempo real.
- La arquitectura debe soportar notificaciones push FCM para cuando las apps están cerradas.
