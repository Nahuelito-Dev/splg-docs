Sobre este Documento

El desarrollo de sistemas intensivos en software se basa en un proceso iterativo e incremental, que consiste en la ejecución sucesiva de las tareas de Análisis, Diseño, Construcción y Pruebas a lo largo de múltiples iteraciones. Este enfoque, propio de la metodología Unified Process (UP) adoptada por la cátedra, permite validar tempranamente las decisiones arquitectónicas, ajustar el alcance ante hallazgos del relevamiento y entregar funcionalidad incremental al cliente.

El presente documento describe el Plan de Iteración previsto para el proyecto SPLG (Sistema de Pedidos y Logística de Garrafas de Gas). Recoge:

  1. Estado actual del proyecto — porcentaje de evaluación de los artefactos, problemas no resueltos y fallas detectadas en iteraciones previas.
  2. Artefactos a producir o refinar en cada iteración, indicando los porcentajes de evaluación que se han de alcanzar al cierre.
  3. Requisitos suplementarios — criterios de calidad, restricciones técnicas y consideraciones que aplican a la iteración.
  4. Pautas de evaluación sobre las que se determinan los puntajes de cada artefacto.

Al término de cada iteración se realizan las evaluaciones pertinentes, cuyos resultados se reseñan en el documento "Cierre de Iteración" con igual código de iteración.

Configuración de la Iteración

Se entiende por Configuración de la Iteración la información que define y da forma a las actividades, metas y características de la misma. Los parámetros que dan forma a cada iteración son:

  • Identificación: código, fase a la que pertenece, fecha de inicio y cierre.
  • Metas: objetivos específicos que persigue la iteración.
  • Artefactos nuevos: documentos o modelos que se inician en la iteración.
  • Artefactos actualizados: artefactos pre-existentes que se refinan o completan.
  • Problemas a resolver: errores o pendientes heredados de iteraciones anteriores.

Requisitos Suplementarios

Requisitos Suplementarios

  • La reserva de stock debe hacerse dentro de una transacción de base de datos con lock pesimista (SELECT FOR UPDATE). Si algo falla, el stock debe revertirse completamente (rollback).
  • El sistema no debe permitir crear un pedido si el stock de cualquier ítem es insuficiente.
  • Al cancelar: si cancela Cliente o Administrador, el stock se restituye. Si cancela el Chofer, el pedido vuelve a PENDING (sin restituir stock).
  • Las promociones por volumen se aplican automáticamente al calcular el total sin intervención del operador.
  • El recargo por transferencia bancaria es del 10% sobre el subtotal de ítems.
  • Se usa decimal.js para todos los cálculos monetarios para evitar errores de precisión con number nativo de JavaScript.

Problemas a Resolver

#ProblemaEstado
1Evitar condición de carrera (race condition) donde dos clientes compran el último stock simultáneamente.Resuelto — transacción con QueryRunner y lock: { mode: 'pessimistic_write' } en la consulta de stock.
2El cron de reintentos podría enviar notificaciones duplicadas para pedidos recién creados (solapamiento con CU-013).Resuelto de otra manera — el modelo cambió a oferta secuencial: cada oferta tiene una ventana de 30 segundos y el ciclo solo procesa las vencidas, de modo que no hay solapamiento.
3Precisión numérica en cálculo de totales con descuentos y recargos (problema del float en JavaScript).Resuelto — uso de decimal.js para todas las operaciones monetarias.
4Definir la lógica del campo dispatchAttempts para el radio progresivo del cron.Resuelto de otra manera — el radio recorre 5, 10, 15 y 20 km buscando el primer chofer sin contactar. No existe un estado de falta de cobertura: agotados los radios, el pedido sigue pendiente y se reintenta en el ciclo siguiente.

Requisitos Suplementarios

  • El entorno de producción debe tener certificado SSL válido para las comunicaciones HTTPS y WSS (WebSocket Secure).
  • El servidor del cliente debe tener al menos 2 GB de RAM y 20 GB de disco disponible para los contenedores Docker.
  • El sistema debe tener backup automático de la base de datos PostgreSQL (script de cron diario).
  • Las credenciales de Firebase Admin SDK y la API key de MercadoPago deben estar configuradas como variables de entorno de Docker (no en el repositorio).
  • Los manuales de usuario deben estar escritos en español y tener imágenes de pantalla reales del sistema.

  • [ ] El administrador del distribuidor puede gestionar el sistema sin asistencia técnica.
  • [ ] Se completaron al menos 5 pedidos reales de prueba de extremo a extremo en producción.
  • [ ] Los 3 manuales de usuario (cliente, chofer, administrador) están redactados y entregados.
  • [ ] Los defectos críticos detectados en las pruebas beta están corregidos y verificados.
